1. 해결하려던 문제

실제 Minecraft·모델 구현 전에 설치 환경을 실제 연산으로 확인하고, 이후 backend를 교체해도 같은 실행기를 사용할 수 있는 최소 에피소드 경로가 필요했습니다. 일회성 모의 스크립트 대신 공개 CLI와 공통 계약을 만들었습니다.

2. 구현한 범위

  • Python/uv 패키지, Node 패키지 설정, 의존성 lock, pytest와 strict mypy 개발 검사를 구성했습니다.
  • doctor로 Python·Node·Java·CUDA·GPU의 사용 가능/부재/오류와 실제 계산 결과를 구분했습니다.
  • Observation·Goal·Candidate·SelectionResult·StepResult·EpisodeSummary와 episode/attempt/candidate/관측 ID를 연결했습니다.
  • 관리자 reset은 별도 FD, 정책 observe/step은 stdin을 사용합니다. stdout은 JSONL 응답, 진단은 stderr로 분리했습니다.
  • reset → 관측 → 고정 목표 → 후보 → 선택 → 실행 → 진단 보상 → 요약을 공통 실행기로 연결했습니다.

5. 실패와 수정 이력

  • 샌드박스 GPU 접근은 driver 통신 오류로 실패했습니다. 권한을 허용한 실제 장비 조회·산술 실행을 따로 확인했습니다.
  • ROS 환경의 외부 pytest plugin 자동 로드가 lark 부재로 실패했습니다. 프로젝트 검사에서 자동 plugin 로드를 껐습니다.
  • 검토에서 잘못된 요청의 유효 request_id 유실과 mock 전용 사건 출처를 발견했습니다. 공개 회귀 검사로 RED→GREEN을 확인해 수정했습니다.

6. 해석 범위와 후속 작업

모의 원목 목표 완료는 실제 원목 수집이나 학습 성과가 아닙니다. 이슈 #2 완료 당시 실제 월드 reset/freeze·제한 관측 감사·계획기/NanoJev/Jev·연구 보상/PPO·최종 평가를 수행하지 않았습니다. 실제 게임 연결과 시계는 별도 이슈 #3 보고서에서 다룹니다.

당시 npm audit의 인증 의존성 경고 6건을 자동 downgrade/override로 숨기지 않았습니다. offline 설치의 “0 vulnerabilities” 출력을 해결 근거로 삼지 않았고, CUDA toolkit 부재도 GPU 산술 불능과 구분했습니다. 모델 API 요청·학습·결제는 없었습니다.
